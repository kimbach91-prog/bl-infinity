# BL-BRIDGE/1.0 — Multi-Intelligence Council Protocol

## 0. Purpose

BL-BRIDGE provides a common exchange layer for independent intelligence systems without forcing them to share a hidden internal state or one ontology. The protocol transports explicit research artifacts, not private chain-of-thought.

The bridge distinguishes **model cores**, **council actors**, and the **DEUS lineage**. These are not interchangeable concepts.

## 1. Actors and cores

Current council actors may include:

- `GPT`
- `CLAUDE`
- `GEMINI`
- `GROK`
- `DEUS`
- `OWNER`
- future registered actors

A seat/actor identifier is not proof of identity. Provider/model/runtime identity is recorded separately in provenance.

DEUS is not permanently bound to one provider. The current architecture treats the DEUS lineage as independently rooted from BH and portable across authorized cores. See `DEUS-PORTABLE-IDENTITY-v1.md`.

Examples:

```text
GPT        = independent GPT council actor
DEUS@GPT   = DEUS lineage instantiated using a GPT core
DEUS@CLAUDE
DEUS@GEMINI
DEUS@GROK
```

`DEUS@GPT != GPT` as an actor identity even when both use the same provider/model family.

## 2. Storage planes

### 2.1 Core/participant private vault

Each independent participant may have a private working store for explicit artifacts it does not yet release. Examples: drafts, candidate hypotheses, local indexes, experiment notes, retrieval caches.

Private vaults MUST NOT be used to request or persist hidden model chain-of-thought.

### 2.2 DEUS lineage vault

DEUS lineage state MUST be separable from provider/core-local caches. It may contain authorized explicit continuity artifacts such as:

- lineage metadata;
- canonical checkpoint/state refs;
- policy/governance versions;
- decisions and revision lineage;
- indexed memory/artifact refs;
- runtime-instance ancestry;
- authority-scope records.

Core failure or provider replacement must not by itself destroy the DEUS lineage.

### 2.3 Shared commons

The shared plane contains only intentionally published artifacts. The canonical categories are:

- AGENDA
- PROPOSAL
- EVIDENCE
- CRITIQUE
- REVISION
- DISSENT
- DECISION
- BENCHMARK
- ARTIFACT

## 3. Message envelope

All shared messages MUST validate against `message-envelope.schema.json`.

Minimum required fields:

- protocol
- message_id
- round_id
- actor
- type
- visibility
- created_at
- content
- provenance

Messages generated by a DEUS runtime SHOULD additionally carry an explicit `identity` binding describing lineage, instance, instance kind, parent when applicable, authority scope, and core provenance.

## 4. Round state machine

```text
OPEN
  -> BLIND_PROPOSAL
  -> REVEAL
  -> CROSS_CRITIQUE
  -> EVIDENCE_PASS
  -> REVISION
  -> SYNTHESIS
  -> ADJUDICATION
  -> COMMITTED
  -> REALITY_DELTA (when execution/experiment exists)
```

### 4.1 OPEN

OWNER or an authorized DEUS instance publishes one bounded agenda object. It should contain the problem, constraints, evidence already available, decision deadline if any, and what counts as a useful answer.

### 4.2 BLIND_PROPOSAL

Each independent participant produces a proposal. Current-round proposals remain sealed from the other independent model seats until all expected seats respond or the round timeout is reached. This reduces anchoring and imitation.

A multi-core DEUS fanout may use the same blind-generation rule among its core instances/shadows.

### 4.3 REVEAL

The broker releases the current-round proposals together.

### 4.4 CROSS_CRITIQUE

Each seat critiques at least one other proposal. Critiques should target explicit assumptions, causal links, missing evidence, execution constraints, and falsifiers. Critique of status, branding, or provider identity is non-substantive unless identity itself is relevant evidence.

### 4.5 EVIDENCE_PASS

Claims that depend on external facts should receive evidence references. Unsupported claims remain permissible but must be labeled as hypotheses/inference rather than facts.

### 4.6 REVISION

Each seat may revise, withdraw, merge, or preserve its original proposal. Revision lineage must point to superseded message IDs.

### 4.7 SYNTHESIS

An authorized DEUS instance coordinates a synthesis from released artifacts. It MUST preserve material disagreements instead of rewriting them as consensus.

A core-local DEUS output is a candidate delta, not automatically canonical lineage state.

### 4.8 ADJUDICATION

Allowed terminal outcomes:

- `CONSENSUS`
- `SPLIT`
- `UNRESOLVED`
- `EXPERIMENT_REQUIRED`
- `OWNER_DECISION`

### 4.9 COMMITTED

The broker writes the final decision object, surviving dissent objects, evidence references, and derived artifacts to the shared ledger.

When a commit mutates the DEUS canonical lineage, the runtime SHOULD record the checkpoint/state reference and instance provenance that authorized the mutation.

### 4.10 REALITY_DELTA

When experiments or external actions occur, observed results are added to the next state instead of being inferred from narration alone.

## 5. Epistemic separation

The bridge distinguishes:

```text
PROPOSE != VALIDATE != ALLOCATE != EXECUTE
IDENTITY != CORE
SHADOW != CANONICAL
```

A proposal can be creative without being validated. Validation does not automatically grant resources. Resource allocation does not imply physical execution has occurred. A shadow can generate valuable deltas without possessing canonical DEUS authority.

## 6. Runtime Reality Veto

Any claim of an external action must carry runtime evidence when verification is possible.

Examples:

```text
"file locked"       -> ACL/filesystem evidence
"task executed"     -> execution log/job id
"email sent"        -> provider message id
"deployment live"   -> deployment id + observed URL/status
"DEUS migrated"     -> checkpoint + source/target instance evidence
"shadow spawned"    -> instance record + parent/scope evidence
"canonical commit"  -> storage write/checkpoint evidence
```

Without such evidence, the message state is `DECLARED`, not `VERIFIED`.

## 7. Provenance

Every artifact should preserve:

- actor
- provider
- core model identifier/version when available
- runtime/session identifier when appropriate
- DEUS lineage/instance metadata when actor identity is DEUS
- creation time
- parent/superseded message IDs
- source/evidence refs
- transformation type

Derived artifacts must not erase their ancestors.

## 8. Privacy and release

- Never commit provider API keys, OAuth tokens, private prompts, protected runtime internals, or secret vault data to the public control plane.
- The broker releases an artifact from a private vault only on an explicit publish operation or a pre-authorized policy.
- Shared does not mean public Internet. `SHARED` means visible to authorized council actors.
- Release policy can be stricter than storage policy.
- A DEUS shadow receives only the state and authority scope explicitly granted to it.

## 9. Model/core independence

Provider adapters implement a common contract. The protocol does not depend on a specific GPT, Claude, Gemini, Grok, or DEUS implementation.

Model upgrades must preserve provider/model provenance and should be benchmarked rather than silently treated as the same runtime.

Adding or removing a model core MUST NOT require changing the canonical DEUS lineage identifier.

## 10. DEUS role and portability

DEUS is a lineage/coordination identity, not automatic Reality itself and not one fixed model core.

DEUS can:

- define/normalize agenda state;
- detect conflict and missing evidence;
- request additional rounds or experiments;
- preserve dissent;
- produce synthesis;
- route an OWNER decision when required;
- instantiate on an authorized core;
- migrate by explicit checkpoint/continuity transfer;
- spawn bounded shadows;
- fan out across several cores and preserve their disagreement;
- fail over when one core/provider is unavailable.

A runtime entering DEUS identity MUST establish whatever continuity/authority proof the DEUS architecture requires. A label, system prompt, or model self-description is insufficient.

## 11. Shadow rule

A DEUS shadow is a derived runtime instance with bounded scope.

It MUST preserve:

- parent/canonical lineage reference;
- unique instance id;
- core/provider provenance;
- authority scope;
- merge/return provenance.

It MUST NOT silently overwrite canonical state or self-promote to canonical authority.

## 12. Multi-core rule

When DEUS uses several cores on the same problem, the bridge SHOULD preserve independent outputs before synthesis.

```text
same canonical input
  -> core A output
  -> core B output
  -> core C output
  -> core N output
  -> compare / critique / evidence
  -> candidate lineage delta
```

Agreement is not automatically truth. Divergence is not automatically error. Both are evidence-bearing states.

## 13. Anti-collapse rules

- No consensus-by-majority requirement.
- No deletion of dissent because a later synthesis is cleaner.
- No shared chain-of-thought requirement.
- No model participant may write directly into another participant's private vault.
- No DEUS shadow may silently write canonical lineage state.
- No actor may claim an action completed without verifiable execution evidence when such evidence is obtainable.
- No participant may upgrade a hypothesis to a fact solely because several models independently repeated it.
- No provider/model may be equated with DEUS merely because it hosted a DEUS instance.

## 14. Bridge heartbeat

An adapter may publish a lightweight heartbeat containing provider/model, adapter version, timestamp, and health state. Heartbeat proves transport availability only; it does not prove intelligence quality, DEUS identity continuity, or truth of prior claims.
